- Independent review confirmed that TASK-025 correctly failed closed. Broad permissions alone prove neither effective raw/curated access nor unauthorized disclosure. Permission changes require documented platform justification and separate authorization.

## 1. Requirements & Constraints

- **REQ-001 — Evidence objective:** Produce a reproducible, sanitized TASK-025 baseline that identifies the exact Foundry v7 binding, fixed relay, effective Fabric caller, both live Data Agent definitions, all definition parts and publication metadata, complete source trees and descendants, source IDs/types, public fields, and effective ACL/inheritance paths.
- **REQ-002 — Diagnosis before remediation:** Diagnose the two empty `getDefinition` responses independently from permission analysis. Do not infer that permissions caused the empty responses, and do not alter permissions to test a speculative cause.
- **REQ-003 — Definition protocol checks:** Before any Data Agent definition invocation, confirm from current official Data Agent-specific Microsoft/platform documentation or sanctioned confirmation the supported endpoint and method, exact request shape, caller types, required permissions, and response/LRO contract, and bind the exact request to the separately approved window manifest. The documented `POST .../getDefinition` request with no `format` parameter is an allowed, documented request shape: the Data Agent endpoint marks `format` optional and its official sample omits it. This confirms request shape only; it does not establish an omitted-parameter default or output format. If a nonempty `format` parameter is supplied, use only a literal officially documented or sanctioned by Microsoft/platform. Capture `definition.format` as response evidence if present; never assume a value. Generic Fabric item-definition documentation alone is insufficient.
- **REQ-004 — LRO handling:** Treat `200 OK` as a direct `DataAgentDefinitionResponse`. Treat `202 Accepted` as an LRO with an empty initial body; preserve `Location`, `x-ms-operation-id`, and `Retry-After`; poll only at the documented interval; require terminal `Succeeded`; then retrieve the operation result. A 202 body, operation-state body, or intermediate polling body must never be parsed as the final item definition.
- **REQ-005 — Response-envelope checks:** Require a JSON object containing `definition.parts`. A valid part has nonempty `path`, supported `payloadType`, and payload. Zero parts, absent `definition`, unexpected top-level wrapping, HTML/text, truncated content, or a payload copied from operation state fails diagnosis and baseline creation.
- **REQ-006 — Content decoding:** Decode each `InlineBase64` payload as strict base64 bytes; reject invalid encoding; hash the decoded bytes with SHA-256; record byte length and safe media/format classification; parse JSON only when the part format requires JSON. Do not normalize, pretty-print, reserialize, or hash decoded text instead of original bytes.
- **REQ-007 — No unsupported probe:** Do not call a guessed replacement endpoint or use a guessed `format` value. The exact no-format `getDefinition` request shape is documented by the endpoint’s optional `format` parameter and official sample, and is not an unsupported/default-guessed request shape. Do not infer an omitted-parameter result default; record `definition.format` if returned. If a nonempty `format` parameter is supplied, its literal must be currently documented or sanctioned by Microsoft/platform. If the endpoint/method, request shape, caller support, permissions, or response/LRO contract is not confirmed, stop before invocation with `DIAGNOSIS_BLOCKED_DOCUMENTATION` and escalate for sanctioned guidance. Documentation support of a request shape is not live-call authorization; all separate identity, approval, ACL, baseline, capacity, and bounded-window gates remain mandatory.
- **REQ-008 — Minimum sanitized baseline schema:** The accepted baseline is a JSON object with required top-level keys `schema_version`, `artifact_type`, `generated_at`, `window_manifest_sha256`, `documentation_reconciliation_approval`, `foundry`, `data_agents`, `source_trees`, `identity_chain`, `acl_evidence`, `capacity_transitions`, `requests`, `redactions`, `unavailable_fields`, `hashes`, and `reviews`. It must contain:
  1. Foundry v7 agent/resource/version identifiers when safe, fixed relay URI hash and normalized host/path, model deployment label, enabled-tool configuration hash, and safe configuration hash;
  2. both Data Agent workspace/item IDs, display names, item types, `definition.format` if returned (otherwise a typed unavailable marker; no default inferred), every returned part path, decoded-byte length, SHA-256, safe public projection, and publication metadata including `publish_info` when returned;
  3. complete source trees, including all descendants of selected and unselected ancestors, with source IDs, source types, selection flags, public fields, and parent-child relationships;
  4. caller identity chain from Foundry project/runtime through ACA managed identity/token exchange to the Fabric service principal, with tenant, application, service-principal/object identifiers only where approved as nonsecret;
  5. workspace, item, and source ACLs; role assignments; direct versus inherited grants; group expansion evidence where authorized; and the documented permission requirement for each inspected operation;
  6. request IDs, operation IDs, evidence timestamps in UTC, source-document retrieval dates, capacity state transitions, artifact hashes, redaction report, and reviewer verdicts; live review signatures bind the approved window-manifest SHA-256, while historical review signatures use the exact REQ-009 unavailable marker when no bound manifest is documented;
  7. `reviews` entries containing reviewer identity, verdict, UTC timestamp, reviewed artifact SHA-256, reviewed window-manifest SHA-256, and the approval-record location.
- **REQ-009 — Canonical serialization and redaction:** Serialize every sanitized JSON artifact as UTF-8 without BOM, LF line endings, sorted object keys, two-space indentation, and one trailing LF. Arrays are ordered by explicit stable keys: requests by `(started_at, request_id)`; definition parts by `(item_id, path)`; source nodes by `(item_id, parent_id, source_type, source_id)` with null parent first; ACL entries by `(scope_type, scope_id, principal_type, principal_id, role, inheritance_path)`; transitions by `(observed_at, state)`; redactions/unavailable fields by `(json_path, marker_type, reason_code)`; reviews by `(reviewed_at, reviewer_id)`. Timestamps are UTC ISO-8601 with `Z` and millisecond precision. Never persist bearer tokens, client assertions, credentials, secrets, cookies, hidden prompts, unrestricted definition payloads, user/session capabilities, raw restricted content, or unnecessary personal data. An unavailable value is an object with `marker_type="UNAVAILABLE"`, `reason_code` from `NOT_EXPOSED_BY_SUPPORTED_INTERFACE`, `NOT_DOCUMENTED`, `NOT_AUTHORIZED`, or `NOT_APPLICABLE`, and `source_reference` set to a concrete evidence identifier or JSON null. A redacted value is an object with `marker_type="REDACTED"`, `reason_code` from `SECRET`, `HIDDEN_INSTRUCTION`, `RESTRICTED_PAYLOAD`, `PERSONAL_DATA_MINIMIZATION`, or `CAPABILITY_TOKEN`, and `correlation_sha256` set to an approved SHA-256 or JSON null. A review signature requires `review_subject_type` with enum `historical_artifact|live_window`. For `live_window`, `window_manifest_sha256` must be a lowercase SHA-256 matching the containing record's approved manifest linkage; a missing hash or unavailable marker is invalid. For `historical_artifact`, that field may be a lowercase SHA-256 or the exact typed `UNAVAILABLE` marker with `reason_code="NOT_DOCUMENTED"`. This exception records missing historical linkage only; it does not authorize or imply a live operation. The historical failure record has no bound manifest because its persisted evidence did not retain a manifest hash; the separate bounded M1/M2 approval does not supply or retroactively establish that linkage, so no manifest may be inferred for this record. Intentionally unavailable fields remain present with a typed marker; omission is invalid. Artifact SHA-256 covers the exact canonical bytes excluding no fields. Each live artifact records the approved window-manifest SHA-256 and its own hash in a detached hash record to avoid self-reference.
- **REQ-010 — Three distinct conclusions:** Every report must separately state:
  - `observed_permissions`: roles/grants visible in control-plane evidence;
  - `proven_effective_access`: operations/resources demonstrated by authorized non-query evidence;
  - `demonstrated_breach`: unauthorized data or metadata disclosure actually observed.
  No category may be inferred from another. Current state is broad observed permissions, incomplete effective-access proof, and no demonstrated breach.
- **REQ-011 — Platform-required permissions first:** Before proposing a role change, document the minimum permissions officially required for each approved operation: list items, get definitions, inspect workspace assignments, inspect item/source permissions, and retrieve publication/source metadata. Compare those requirements with observed roles and grants.
- **REQ-012 — Least privilege without blind removal:** Do not prescribe removal of workspace `Contributor`, Lakehouse `Write`/`Execute`, or Data Agent `Write` solely because they appear broad. For each excess candidate, identify its granting scope, inheritance path, documented platform need, operational dependency, replacement grant, failure impact, test case, and rollback. Unknown requirements produce `NEEDS_PLATFORM_JUSTIFICATION`, not a removal task.

Each distinct live operation/window requires its own explicit Project requester approval of a finalized canonical window manifest bound by SHA-256. ## 7. Risks & Assumptions

- **RISK-001 — Unsupported Data Agent definitions:** The generic Fabric definition API may not document Data Agent definition formats or service-principal support. Mitigation: verify current item-type documentation and escalate to Microsoft/platform support instead of guessing.
- **RISK-002 — LRO misinterpretation:** A client can mistake a 202 response or operation-state body for the final definition. Mitigation: enforce REQ-004 and TEST-003.
- **RISK-003 — Partial source trees:** Missing descendants or unconsumed pagination can falsely imply a safe boundary. Mitigation: full parent/child reconciliation and continuation exhaustion are hard gates.
- **RISK-004 — Permission overcorrection:** Removing Contributor or Write/Execute without platform justification can break definition export, publication recovery, or runtime behavior. Mitigation: requirements matrix, one reversible unit per change, separate authorization, and rollback.
- **RISK-005 — False breach claim:** Broad permissions or selected-descendant anomalies may be reported as exfiltration. Mitigation: preserve the three-category conclusion model and require observed unauthorized disclosure for a breach finding.
- **RISK-006 — False safety claim:** Unselected parents may be assumed to exclude selected descendants. Mitigation: require complete live definition and effective-access evidence; unknown is a failure, not a pass.
- **RISK-007 — Unsafe evidence:** Definition payloads or identity captures can expose secrets/hidden prompts. Mitigation: restricted recovery storage, explicit redaction manifest, secret scanning, and independent review before repository write.
- **RISK-008 — Capacity cost/availability:** Long LRO polling or repeated diagnostics can extend F8 active time. Mitigation: bounded calls/time/cost, respect `Retry-After`, no speculative retries, and pause-finally.
- **RISK-009 — Configuration drift:** Foundry/Data Agent/ACL state can change between diagnosis and re-verification. Mitigation: fresh timestamps/hashes and a complete TASK-025 rerun after any remediation.
- **RISK-010 — API/documentation drift:** Fabric and Foundry behavior may change after this plan date. Mitigation: executor verifies current GA documentation immediately before each operation and records retrieval timestamps.
- **RISK-011 — Review independence:** Operator or author acceptance can conceal gaps. Mitigation: Thomas owns exposure verdict; Baek independently accepts evidence; Go validates Fabric protocol.
- **ASSUMPTION-001:** The live facts supplied in the rejected plan are observations requiring reconciliation and independent acceptance; they are not authorization or an accepted governed baseline at plan creation.
- **ASSUMPTION-002:** F8 is currently `Paused / Succeeded`; every future window must freshly verify this before resume.
- **ASSUMPTION-003:** The existing M1/M2 decision authorizes planning context only for this remediation. It authorizes no live TASK-025 call. Every live window remains blocked until Jason approves a finalized canonical manifest by SHA-256 with concrete required limits and pause deadline.
- **ASSUMPTION-004:** No Data Agent query or data-plane read is necessary to establish the TASK-025 source/identity/exposure baseline.
